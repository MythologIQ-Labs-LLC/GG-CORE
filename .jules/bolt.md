## 2024-05-24 - [O(N) to O(1) PageTable Lookups in KV-Cache Memory Manager]
**Learning:** Found a major performance bottleneck where the `PageTable` implementation in `paged.rs` was using an O(N) linear scan (`self.pages.iter().find(|p| p.id == *page_id)`) to find pages by ID, despite the fact that `PageId` corresponds exactly to the page's index in the `self.pages` vector (since pages are assigned sequentially and never removed). This means every token generation and attention score calculation in the KV cache was executing an O(max_pages) search.
**Action:** Replaced the O(N) linear scans with O(1) direct array accesses (`self.pages.get(page_id.0)`). When dealing with memory pools or arenas where IDs are assigned sequentially, always check if the ID can be used as a direct index to avoid unnecessary O(N) lookups.
## 2024-05-25 - [O(N) to O(1) Allocations in Sliding Window Token Matching]
**Learning:** Found a major performance bottleneck where sliding window calculations in `has_excessive_repetition` (in `core-runtime/src/security/sanitizer_rules.rs`) used `window.join(" ")` to construct a newly allocated `String` on the heap for every 3-word window step. This means a 100k-word document caused 100k independent heap allocations for HashMap lookups, slowing the thread.
**Action:** Replaced the `String` allocations with `&[&str]` as the HashMap key. Because Rust's slice references natively implement `Hash` and `Eq`, they can directly index into hash maps. Also introduced early returns within the window loop (`if *count > 5`) to short-circuit instead of computing the entire sequence map. Always pass `&[&T]` into HashMaps instead of joining `&[T]` windows into strings/vectors if you only need them for counting or lookup.
