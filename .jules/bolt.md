## 2024-05-24 - [O(N) to O(1) PageTable Lookups in KV-Cache Memory Manager]
**Learning:** Found a major performance bottleneck where the `PageTable` implementation in `paged.rs` was using an O(N) linear scan (`self.pages.iter().find(|p| p.id == *page_id)`) to find pages by ID, despite the fact that `PageId` corresponds exactly to the page's index in the `self.pages` vector (since pages are assigned sequentially and never removed). This means every token generation and attention score calculation in the KV cache was executing an O(max_pages) search.
**Action:** Replaced the O(N) linear scans with O(1) direct array accesses (`self.pages.get(page_id.0)`). When dealing with memory pools or arenas where IDs are assigned sequentially, always check if the ID can be used as a direct index to avoid unnecessary O(N) lookups.
## 2024-05-25 - [O(N) String Allocations in has_excessive_repetition]
**Learning:** Found a performance bottleneck in `core-runtime/src/security/sanitizer_rules.rs` where `has_excessive_repetition` was creating a new `String` for every 3-word window (`window.join(" ")`) to use as a `HashMap` key. This caused O(N) heap allocations for an N-word text string. Rust slices (`&[&str]`) implement `Hash` and `Eq` natively.
**Action:** Replaced the `HashMap<String, usize>` with `HashMap<&[&str], usize>` and used the slice reference `window` directly as the key. This completely eliminates the heap allocations inside the loop, turning O(N) allocations into O(0) allocations. When calculating occurrences over sliding windows of words or tokens, always use the slice reference `&[&T]` directly as the `HashMap` key instead of joining or allocating a new `String` or `Vec<T>`.
