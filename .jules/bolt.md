## 2024-05-24 - [O(N) to O(1) PageTable Lookups in KV-Cache Memory Manager]
**Learning:** Found a major performance bottleneck where the `PageTable` implementation in `paged.rs` was using an O(N) linear scan (`self.pages.iter().find(|p| p.id == *page_id)`) to find pages by ID, despite the fact that `PageId` corresponds exactly to the page's index in the `self.pages` vector (since pages are assigned sequentially and never removed). This means every token generation and attention score calculation in the KV cache was executing an O(max_pages) search.
**Action:** Replaced the O(N) linear scans with O(1) direct array accesses (`self.pages.get(page_id.0)`). **Learning:** Found a performance bottleneck in `has_excessive_repetition` where the algorithm was allocating new strings to use as a HashMap key. This creates significant overhead, especially for long output texts where the window sizes are generated via `.windows(3)`.
**Action:** Replaced `window.join(" ")` with using the slice reference `&[&str]` as the HashMap key. Rust slices implement `Hash` and `Eq` correctly, avoiding strings allocations when counting occurrences.
